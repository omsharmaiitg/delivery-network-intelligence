## Problem Statement

Delhivery's current routing engine (OSRM) systematically underestimates delivery times — **95% of legs run more than 20% over OSRM estimates**, and delay is not uniformly distributed. A small number of hub facilities and corridors are responsible for a disproportionate share of the network's total excess delay. This project identifies those bottlenecks, builds a graph-enhanced ETA model that dramatically outperforms OSRM, and quantifies the business impact of targeted hub upgrades.

```bash
# 1. Install dependencies (numpy pinned <2 for gensim/node2vec compatibility)
pip install -r requirements.txt

# 2. Place the raw dataset
# Download delivery_data.csv (~55 MB) and place at:

python src/02_graph_construction.py  # Legs        → graph + edges/nodes
python src/03_bottleneck_audit.py    # Centrality  + SLA-breach contribution
python src/04_eta_models.py          # Baseline vs graph-enhanced ETA model
python src/05_ftl_carting.py         # Route-type decision framework
python src/06_visualizations.py      # All figures → outputs/figures/
python src/07_impact_scenario.py     # Top-3 hub upgrade impact numbers

# 4. Launch the dashboard (optional)
streamlit run app.py
```

> All modules are ordered — each writes artifacts the next one reads. Results are fully reproducible with `SEED = 42` throughout.

## Model Performance

| Model | MAE (min) | RMSE (min) | On-target ±15% | On-target ±25% |
|-------|-----------|------------|----------------|----------------|
| OSRM (current engine) | 107.8 | 234.1 | 4.1% | 8.4% |
| Ridge baseline | 198.3 | 1510.5 | 18.8% | 32.3% |
| XGBoost (trip features only) | 34.2 | 78.2 | 45.5% | 64.1% |
| **XGBoost + Graph (ours)** | **27.8** | **72.6** | **58.3%** | **75.6%** |

**Graph advantage over trip-only baseline: −18.9% MAE, +12.8 pts on-target** (measured on held-out test set, no leakage).

## FTL vs Carting Decision Framework

| Distance Band | Recommendation | Avg Time Saved |
|---------------|---------------|----------------|
| < 50 km | Carting | — |
| 50–150 km | Carting | — |
| 150–400 km | Mixed (32% FTL) | 111 min |
| 400–800 km | **FTL (100%)** | 339 min |
| > 800 km | **FTL (100%)** | 778 min |

Framework recommends FTL on **7% of stable corridors (145/1,934)** — the long-trunk lanes where reliability premium outweighs cost.

## Methodology Notes

**Data model** — Each raw row is a scan; cumulative `actual_time`/`osrm_time` reset per leg, so the max-cumulative row of each `(trip, source, dest)` group is the leg total.

**Edge weights** — Median delay ratio per corridor, stratified by route type and time of day. Median over mean for robustness to the long right tail.

**Bottleneck scoring** — Hubs ranked by **share of total network excess-delay minutes** (business-readable), with centrality explaining structural importance. Binary ">20% breach" avoided since it is near-universal (95% of legs).

**ETA model** — Target = `log1p(actual_time)`. Graph features (betweenness, PageRank, degree, node2vec embeddings, corridor history priors) learned on **train fold only**, merged to test with corridor → state-pair → global cold-start fallback. No leakage.

**FTL vs Carting** — Route type is not randomly assigned, so we model the **delay ratio** counterfactually. Decision = generalized cost `money + value-of-time + SLA-penalty · (1 + 3·betweenness) · P(breach)`.

**Business assumptions** — All cost constants (FTL/Carting rates, revenue-at-risk per leg) are explicit and configurable at the top of `src/05` and `src/07`. The framework is the deliverable; plug in real Finance numbers to get precise rupee figures.

## Dashboard

The Streamlit dashboard (`app.py`) provides a live operations console with four tabs:

- **Bottleneck Hubs** — ranked table + interactive map
- **Corridor Delay** — chronic delay corridors with excess minutes
- **ETA Predictor** — model comparison and feature importance

## Dataset

Public Delhivery feature-engineering dataset — ~144,900 scans / 14,800 trips over a ~25-day window (Sep–Oct 2018). Raw file (`delivery_data.csv`, ~55 MB) is excluded from this repo due to size; all generated artifacts are included so the dashboard and memo work without re-running.
